📉 1. Otimização de Leitura (Evitar Esgotamento do Plano Spark)

  O Plano Spark oferece 50.000 leituras de documentos por dia. O modelo atual da sua aplicação
  esgotará essa cota muito rapidamente.

   * Problema Crítico: Consultas Completas de Coleções (getDocs)
      Arquivos como members.service.ts, finance.service.ts e stock.service.ts fazem a leitura de
  todos os documentos da coleção de uma só vez:
   1     const colRef = collection(this.firestore, this.COL);
   2     return from(getDocs(colRef)).pipe(...) // Puxa a coleção inteira!
      Cenário: Se você tiver 1.000 membros cadastrados e 3.000 lançamentos financeiros, toda vez que
  um usuário (ou a renovação do cache de 15 min) abrir a página, o Firebase consumirá 4.000
  leituras. Se 10 usuários acessarem o sistema algumas vezes, seu limite diário acaba em horas.
       * Solução: Implemente Paginação. Use as funções limit() e startAfter() do Firestore. Na
         listagem de transações e membros, traga apenas os primeiros 30 a 50 itens e crie um botão
         "Carregar mais".

   * Problema Crítico: Dashboard "Sugador" de Leituras
      No arquivo dashboard.ts, o sistema baixa todos os membros, todo o estoque e todas as
  transações apenas para somar valores e contar a quantidade:

   1     // Baixa tudo para o navegador apenas para calcular totais:
   2     this.kpis.activeMembers = members.filter(m => !m.deleted).length;
   3     this.kpis.balance = active.reduce((sum, t) => sum + t.value, 0);
      Isso é letal para as cotas. Cada documento lido conta contra o limite.
       * Solução: Utilize as funções nativas de Agregação do Firestore (getCountFromServer e
         getAggregateFromServer). O Firebase introduziu recentemente a função de soma (sum()) e
         contagem (count()). Elas cobram 1 leitura a cada 1.000 documentos processados, em vez de 1
         leitura por documento.

  📈 2. Otimização de Escrita (Limite de 20.000/dia)

   * Invalidação Agressiva de Cache
      Sempre que você salva, edita ou deleta algo (ex: softDelete no finance.service.ts), o sistema
  faz:
   1     tap(() => localStorage.removeItem(this.TIME_KEY))
      Isso força a próxima visita à tela a ignorar o cache local e fazer o download de toda a
  coleção do zero novamente.
       * Solução: Quando houver um "salvar", "editar" ou "deletar" com sucesso no backend, em vez de
         invalidar o cache, atualize o cache local no localStorage. Insira, altere ou remova o item
         da lista JSON já armazenada. Isso evitará requisições massivas desnecessárias no backend.

  🔒 3. Segurança de Dados e Vazamentos

  O sistema apresenta algumas armadilhas na integração entre Angular (Frontend) e Firestore Rules
  (Backend).

   * Vazamento de Permissões (Conflito Frontend vs Backend)
      No auth.service.ts, o Angular consulta duas tabelas de permissão: a individual do usuário
  (permissions/${email}) e a do cargo (permissions/role_${role}).
      No entanto, em firestore.rules, as funções hasPermissionDoc() e getP() consultam apenas a
  permissão individual (o email):

   1     function getP() {
   2       return
     get(/databases/$(database)/documents/permissions/$(request.auth.token.email)).data;
   3     }
      Consequência: Se você criar uma regra onde um usuário pode cadastrar um membro apenas porque o
  "cargo" dele permite, o Frontend vai exibir o botão "Novo Membro". Porém, ao salvar, o servidor
  (Rules) vai dar erro Missing or insufficient permissions porque a regra do backend ignora
  totalmente a existência dos cargos (role_*).
       * Solução: Adicione a avaliação do cargo do usuário dentro do arquivo firestore.rules
         (passando o cargo no token ou lendo o documento de role) OU replique as permissões do cargo
         diretamente no documento de permissão de cada usuário no momento que o cargo é atribuído.

   * A Armadilha do "Rules Are Not Filters"
      A regra diz que o usuário logado só pode ler seu próprio documento de membro:
  resource.data.email == request.auth.token.email.
      No entanto, quando um membro comum abre a tela inicial e o frontend tenta buscar todos os
  membros (getDocs(collection('members'))), a query não é filtrada pelo email. O Firebase avaliará a
  requisição e negará o acesso à requisição inteira com erro, pois o usuário está "tentando ler a
  coleção inteira sem ter acesso a ela toda".
       * Solução: As requisições do Angular devem refletir as regras. Se o usuário só pode ler seus
         próprios dados, o getDocs precisa usar uma query restrita: query(collection('members'),
         where('email', '==', userEmail)).

   * Regras Abertas no Firebase Storage
      O arquivo storage.rules atualmente permite leitura e gravação universais:

   1     allow read, write: if true;
      Qualquer pessoa (mesmo não logada e mal-intencionada) que descobrir a chave do projeto pode
  enviar gigabytes de lixo, estourando rapidamente seu limite de armazenamento do Spark (1 GB).
       * Solução: Altere ao menos para allow read, write: if request.auth != null; (para limitar a
         usuários logados).

   * Falta de Isolamento nos "Soft Deletes"
      A exclusão lógica marca os documentos com deleted: true. Mas as regras do Firebase
  (firestore.rules) não obrigam a checagem desse campo. Qualquer usuário do sistema autorizado a ler
  membros ou finanças pode manipular requisições manualmente via API para visualizar dados
  financeiros ou membros "deletados".
       * Solução: Mantenha os soft-deletes restritos no backend também. Altere as consultas do
         Angular para SEMPRE incluir where('deleted', '==', false) e adicione em firestore.rules uma
         trava validando: allow read: if resource.data.deleted == false.

  🛒 2. O que falta para ter um PDV (Ponto de Venda / Página de Vendas)

  Para gerenciar uma Cantina, Lojinha de Artigos Religiosos ou venda de ingressos de eventos, você
  precisa de um Módulo de Vendas (PDV).

  O que precisa ser desenvolvido no Angular e Firebase:
   1. Tela de Frente de Caixa (PDV): Uma interface rápida (estilo supermercado/lanchonete) onde o
      operador pode adicionar itens ao "carrinho" clicando em botões grandes ou lendo código de
      barras.
   2. Integração Estoque -> Venda: Ao finalizar uma venda, o sistema deve subtrair automaticamente a
      quantidade dos produtos no módulo de Estoque.
   3. Integração Venda -> Financeiro: A venda concluída deve gerar automaticamente uma "Transação de
      Entrada" no Financeiro, atrelada à categoria "Vendas/Cantina".
   4. Fechamento de Caixa: Uma rotina para abrir o caixa no início do dia/gira e fechar no final,
      conferindo se o dinheiro físico/PIX bate com o registrado no sistema.
   5. Forma de Pagamento: Registrar no momento da venda se foi PIX, Dinheiro, Cartão de
      Crédito/Débito ou "Fiado" (pendente na conta do membro).

  📊 3. O que falta no Financeiro para gerar um DRE (Demonstrativo de Resultados)

  O DRE (Demonstração do Resultado do Exercício) é um relatório contábil que mostra se o Centro deu
  Lucro ou Prejuízo em um período detalhando a natureza dos gastos. O seu modelo atual (Transaction)
  tem apenas description, value, type e category. Isso é um "Livro Caixa", não atende a
  contabilidade profissional.

  O que você precisa adicionar na modelagem (transaction.model.ts):

   1. Plano de Contas Estruturado (Hierarquia de Categorias):
      Em vez de uma category simples em texto livre, você precisa de um Plano de Contas
  classificado. Exemplo:
       * 1. Receitas (1.1 Mensalidades, 1.2 Doações, 1.3 Cantina, 1.4 Eventos).
       * 2. Custos Operacionais / CMV (2.1 Compra de mercadorias para revenda).
       * 3. Despesas Operacionais (3.1 Aluguel, 3.2 Energia, 3.3 Água, 3.4 Manutenção, 3.5 Material
         de Limpeza, 3.6 Velas/Charutos para uso do terreiro).
   2. Centro de Custos:
      Para saber de onde o dinheiro está saindo ou entrando. Ex: "Terreiro", "Cantina", "Obras",
  "Festa de Exu". Isso permite saber se a cantina se paga ou se o terreiro está bancando ela.
   3. Status do Pagamento (Contas a Pagar/Receber):
      Adicionar o campo status: 'Pendente' | 'Pago' | 'Cancelado' | 'Vencido'.
      O DRE pelo regime de competência exige saber quando a despesa ocorreu, mesmo que ainda não
  tenha sido paga.
   4. Datas Distintas (Emissão vs Vencimento vs Pagamento):
      Hoje só existe date. O correto para a contabilidade é:
       * issueDate (Data do documento/nota fiscal).
       * dueDate (Data de vencimento).
       * paymentDate (Data em que o dinheiro efetivamente saiu/entrou na conta).
   5. Anexos / Comprovantes:
      Campo receiptUrl: string (salvo no Firebase Storage) para o tesoureiro anexar a foto da nota
  fiscal ou recibo da despesa. Contadores exigem o comprovante para lançar no DRE oficial.
   6. Conta Bancária / Destino:
      Adicionar accountId ou bank (Ex: "Caixinha Físico", "Conta Nubank", "Conta PagSeguro"), para
  facilitar a conciliação bancária.
